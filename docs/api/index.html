Endpoint reference for /api/v2, the HTTP API of HumHub core (1.20+). Endpoints are grouped by the module that owns them; the sidebar lists every operation, and the search covers all of them.

Status: internal use only

/api/v2 exists to serve the platform's own user interface — every endpoint here has a Vue island as its first consumer — and is documented so that the contract is explicit rather than implied by the client code. It is not yet a public, stable API: while the surface is being completed, an endpoint or a shape may still change between releases without a deprecation period, and not every resource is covered.

The goal is a complete, stable API that third-party clients can build on. Once a resource is declared stable, changes to it will be additive only — fields are neither removed nor renamed, enums may grow (a client must tolerate unknown values), and anything breaking goes into a new generation. Until then, integrations should keep using the /api/v1 surface of the REST API module — see its manual.

The REST API module also contributes the token authentication methods these endpoints accept. HumHub's own browser session is accepted too, which is what the platform's Vue UI uses; state-changing session requests additionally require the CSRF token (X-CSRF-Token header or _csrf body parameter). For the design of this stack see docs/develop/concept-api.md.

Conventions

Fixed for this API generation, and differing from /api/v1:

  • Everything under /api/ answers JSON, errors included — an unknown route or a verb an endpoint does not take gives a JSON 404 like any other error.
  • Timestamps are ISO-8601 with offset, in UTC (2026-08-22T08:00:00+00:00).
  • Field names are camelCase throughout — including the keys of validation errors, so a client matches them against the field names it sent. Enums are named values (state: member, visibility: public), never stored integers.
  • Records are addressed by numeric id: the record's own id in a path, the platform-wide recordId for anything likeable (like/<recordId>), the contentContainerId of a space or user where a container is meant (containerId). Guids appear in payloads for display, never as an address. Class names never reach the wire.
  • Where a parameter travels follows the verb: what identifies or filters a read goes in the query string, what a POST creates, a PATCH changes or a PUT sets goes in the JSON body (the target included), and a DELETE takes its options in the query string. PATCH is the one update verb of a record and is partial — a field left out keeps its value.
  • Errors are plain HTTP status codes with a JSON body; there is no {code, message} success/failure envelope. Validation failures — a missing required parameter included — answer 422 with {"errors": {"<field>": ["<message>"]}}. Creating a resource answers 201, a state transition 200 with the new state, a successful delete 204.
  • A state of the caller towards something — a relationship it can read back — is a resource noun under its target (like/<recordId>, space/<id>/membership, user/<id>/friendship): GET reads it, PUT sets it and DELETE removes it. Both writes are idempotent, as HTTP defines them: setting what is already set and removing what is already gone succeed and answer the current state, so a client acting on a stale view ends up with the truth.
  • An operation the caller triggers on the system is a verb sub-path taking POST (marketplace/module/<id>/install, module/<id>/enable, notification/mark-as-seen). Whether something is one or the other is decided by the question "can the caller read it back as a state?" — if so, it is a resource.
  • Records are created with POST on their collection, changed with PATCH and deleted with DELETE.
  • Lists that hold still page by offset and use {results, total, page, pageSize, pages}. Lists that reorder while being read (activity, notification) page by cursor + limit and carry a nextCursor. Comment threads are windows paged in both directions (cursor + direction, or focus, plus limit) that carry their remaining counts.
  • Payloads are caller-neutral wherever possible — identical for every reader who may see the record, and therefore cacheable. What depends on the caller (permissions, like state, membership) has endpoints of its own.

Rich text

A rich text field such as a comment's message is HumHub richtext markdown: CommonMark with tables and strikethrough, plus a few additions the platform resolves itself (see docs/develop/concept-richtext.md):

  • [Jane Doe](mention:<guid> "<url>") mentions a user or space. The text is the display name and the title the profile URL, both current at serialization time.
  • [report.pdf](file-guid:<guid> "<url>"), or ![alt](file-guid:<guid> "<url>") for an image, refers to an attached file. The record's files array carries the same file under that guid, with its URLs and thumbnails.
  • [<url>](oembed:<url>) marks a link that renders as an embedded preview. The URL itself is the fallback link. Whether a reader sees the preview depends on their oembed consent, so the payload never contains it; a client fetches previews itself.
  • :smile: style shortcodes stand for emoji.

Everything else is standard markdown. A client that displays the field needs a link hook for these three URL schemes; a client that edits it sends the same format back. It is the canonical, lossless representation — a converted form (plain markdown, HTML) would lose the guid bindings and is not accepted on write.

Activity

Always what the caller may see. Without containerId the list spans every container the caller subscribes to (the dashboard box), with it the one container named (the box on a space or profile). Activities the caller may not see never appear, and the caller's own activities are left out — the box has always shown what others did.

Cursor paging instead of page numbers. The list reorders as activities arrive and groups form, which page numbers cannot express without skipping or repeating entries. A page carries a nextCursor to hand back, null once the list is exhausted. The cursor is opaque: pass it back untouched, never build one from an entry.

Grouping is the server's. Several activities of a kind on the same content count as one entry, which reports how many it stands for in groupCount and says so in its sentence ("Jane and 2 others"). An entry is identified by key, not by id; see the schema for why neither is durable.

The sentence comes from the server. An activity's message is the localized, module-defined phrase — the one part a client cannot build. Everything around it (avatar, space badge, relative time, link) is data in this payload, rendered by the client.

Comment

Comment lists are cursor windows, not offset pages (see the window endpoints): a window is addressed by cursor + direction, by focus, or by nothing, and sized by limit.

The comment shape is caller-neutral: identical for every reader who may see the content. What depends on the caller has its own endpoints — GET /comment/{id}/permissions for edit/delete, GET /like/states for like state.

Root comments of a content

/api/v2/content/{id}/comments

A window of the content's root comments. Without any parameter the newest comments are returned; cursor + direction page from a comment the client already has ("show previous/next N comments"), focus centres the window on a permalinked comment. limit sizes whichever window that is.

total counts all comments of the content including replies (what a comment badge shows), while results, prevCount and nextCount describe the root level only. rootTotal is the root-only total a root list needs to compute its own remaining count.

Readable by guests for guest-visible content while guest access is enabled platform-wide, unless the comment module hides comments from guests (guestHideComments).

Content

The context menu of a content record — the data behind the ⋮ menu a stream entry or a module's own list shows. It is deliberately its own endpoint rather than part of any content payload: everything it returns depends on who is asking, so folding it into a record shape would make that shape uncacheable and different for every reader. The same split the comment API makes with GET /comment/{id}/permissions.

The context menu of a content record

/api/v2/content/{id}/controls

Resolves the record's WallEntryControls widget stack — every WallEntryControls::EVENT_INIT handler included — and returns it as data instead of markup, together with what the caller may do with the record.

This is what the ContentControls Vue island loads when its menu is opened, and it is why a module that has contributed a control link for years keeps working in a client-rendered menu without any change: menu links (core's own entries among them) and legacy control-link widgets arrive as descriptors, and only other widgets fall back to the deprecated html escape hatch.

Loaded lazily, on menu open — a list of 50 rows costs no request at all until someone actually opens a menu.

File

Uploading is a batch operation. A single request carries any number of files, and the response reports the outcome per file — one rejected file never discards the accepted ones. That is the one documented deviation from the 422 {"errors": …} validation contract of this API generation: a rejected file is a batch item, not an invalid field.

Files arrive unattached. Nothing is bound to a record here: a client uploads, keeps the returned guids and submits them with the form that owns them (fileList for a comment). Removing a file before saving is therefore purely client-side — the file stays unattached and the platform's own cron job cleans it up.

Upload files

/api/v2/file

Stores the uploaded files for the authenticated caller. Same model, validation and image downscaling as the platform's own upload widget, so both paths produce identical files.

The response carries the stored files in results and, per rejected file, its name and validation messages in errors. The status is 200 whenever the request carried at least one file — even if every single one was rejected. A request with no file at all is a malformed request and answers 422.

Marketplace

The modules of the HumHub marketplace as this installation sees them — for module administrators (ManageModules), absent (404) while the marketplace is disabled. The catalogue comes from humhub.com; while it cannot be reached the list and the categories answer 503.

Every shape here describes the installation, not the caller: two administrators asking at the same time get the same answer. Enabling an installed module is not marketplace business and lives in the Module API (POST /module/{id}/enable).

Notification

Always the caller's own notifications. There is no user parameter, and no action here is reachable for a guest. (The module's /api/v1 notification endpoints, which let an admin token read another user's notifications, are unaffected.)

Cursor paging instead of page numbers. The list is ordered unseen-first, newest-first, and it reorders while a user pages through it — notifications arrive, others are read. Page numbers would silently skip or repeat entries, so a page carries a nextCursor to hand back, and null once the list is exhausted. This is the one list of this API generation that does not use the {results, total, page, pageSize, pages} envelope.

The sentence comes from the server. A notification's html is the localized, module-defined phrase ("Jane commented on Post 'Release notes'") — the one part a client cannot build. Everything around it (avatar, space badge, relative time, unread marker) is data in this payload, rendered by the client.

The caller's notifications

/api/v2/notification

One page of the caller's notifications, unseen first and newest first. Grouped notifications (several likes on the same post, say) count as one entry.

A notification whose source no longer exists — its content was deleted, its class left with an uninstalled module — is dropped from the list (and from the database) instead of failing the request, so a page may contain fewer entries than limit even when nextCursor is set.

/api/v2/user/{id}/follow

The caller's follow relationship to the user, and whether following can be started (see the UserFollowState schema). 403 for the caller's own user — there is no follow relationship to oneself — and for a disabled or deleted user.

Follow a user

/api/v2/user/{id}/follow

Follows the user, with notifications. Answers the new state, in the same shape GET returns. Idempotent: following a user already followed changes nothing and answers the state.

403 where following is not possible: while following is disabled, for the caller's own user and for a disabled or deleted user.

Stop following a user

/api/v2/user/{id}/follow

Ends the caller's follow of the user and answers the new state. Unfollowing a user who is not followed is a success, and ending a follow stays possible after following was disabled. 403 for the caller's own user and for a disabled or deleted user.
