HumHub HTTP API (v2) (2.0.0)

Download OpenAPI specification:

E-mail: info@humhub.com License: AGPLv2

Endpoint reference for /api/v2, the HTTP API of HumHub core (1.20+). Endpoints are grouped by the module that owns them; the sidebar lists every operation, and the search covers all of them.

/api/v2 is still being built out and does not cover every resource yet. Where an endpoint is missing, the /api/v1 surface of the REST API module can be used alongside it — see its manual.

The REST API module also contributes the token authentication methods these endpoints accept. HumHub's own browser session is accepted too, which is what the platform's Vue UI uses; state-changing session requests additionally require the CSRF token (X-CSRF-Token header or _csrf body parameter). For the design of this stack see docs/develop/concept-api.md.

Conventions

Fixed for this API generation, and differing from /api/v1:

  • Timestamps are ISO-8601 with offset, in UTC (2026-08-22T08:00:00+00:00).
  • Field names are camelCase throughout — including the keys of validation errors, so a client matches them against the field names it sent.
  • Errors are plain HTTP status codes with a JSON body; there is no {code, message} success/failure envelope. Validation failures answer 422 with {"errors": {"<field>": ["<message>"]}}, a successful delete answers 204.
  • Paginated lists use {results, total, page, pageSize, pages}. Lists that reorder while being read (activity, notification) page by cursor instead and carry a nextCursor.
  • Payloads are caller-neutral wherever possible — identical for every reader who may see the record, and therefore cacheable. What depends on the caller (permissions, like state, membership) has endpoints of its own.

Activity

Always what the caller may see. Without containerGuid the list spans every container the caller subscribes to (the dashboard box), with it the one container named (the box on a space or profile). Activities the caller may not see never appear, and the caller's own activities are left out — the box has always shown what others did.

Cursor paging instead of page numbers. The list reorders as activities arrive and groups form, which page numbers cannot express without skipping or repeating entries. A page carries a nextCursor to hand back, null once the list is exhausted. The cursor is opaque: pass it back untouched, never build one from an entry.

Grouping is the server's. Several activities of a kind on the same content count as one entry, which reports how many it stands for in groupCount and says so in its sentence ("Jane and 2 others"). An entry is identified by key, not by id; see the schema for why neither is durable.

The sentence comes from the server. An activity's message is the localized, module-defined phrase — the one part a client cannot build. Everything around it (avatar, space badge, relative time, link) is data in this payload, rendered by the client.

The activities the caller may see

/api/v2/activity

One page of activities, newest group first.

An activity whose class or records no longer resolve — its module was uninstalled, the content it is about is gone — is skipped instead of failing the request, so a page may contain fewer entries than limit even when nextCursor is set.

Comment

Comment lists are cursor windows, not offset pages (see the window endpoints).

The comment shape is caller-neutral: identical for every reader who may see the content. What depends on the caller has its own endpoints — GET /comment/{id}/permissions for edit/delete, GET /like/states for like state.

Root-comment window of a content

/api/v2/comment/content/{id}/window

A window of the content's root comments. Without any cursor the newest comments are returned; commentId + direction pages from a comment ("show previous/next N comments"), commentId alone focuses the window around a permalinked comment.

total counts all comments of the content including replies (what a comment badge shows), while results, prevCount and nextCount describe the root level only. rootTotal is the root-only total a root list needs to compute its own remaining count.

Readable by guests for guest-visible content while guest access is enabled platform-wide, unless the comment module hides comments from guests (guestHideComments).

Content

The context menu of a content record — the data behind the ⋮ menu a stream entry or a module's own list shows. It is deliberately its own endpoint rather than part of any content payload: everything it returns depends on who is asking, so folding it into a record shape would make that shape uncacheable and different for every reader. The same split the comment API makes with GET /comment/{id}/permissions.

The context menu of a content record

/api/v2/content/{id}/controls

Resolves the record's WallEntryControls widget stack — every WallEntryControls::EVENT_INIT handler included — and returns it as data instead of markup, together with what the caller may do with the record.

This is what the ContentControls Vue island loads when its menu is opened, and it is why a module that has contributed a control link for years keeps working in a client-rendered menu without any change: entries that can describe themselves (humhub\widgets\menu\DescribableWidget) arrive as descriptors, and only those that cannot fall back to the deprecated html escape hatch.

Loaded lazily, on menu open — a list of 50 rows costs no request at all until someone actually opens a menu.

Authorizations:
BearerBasicAuthSessionCookie
path Parameters
id
required
integer

The content id — the primary key of the content record, not the primary key of the owning model (a post, a file, an event).

string
Enum: "default" "dashboard" "search" "detail" "modal"

Where the menu is being shown. Selects the render-options profile a server-rendered menu would have used in the same place, so a menu inside a module's own UI is not offered stream-only actions. Omit for the default profile.

string

Comma-separated list of core entries the caller renders itself and does not want from the server. A host with its own Edit action would otherwise receive a second, server-rendered one next to it.

Uploading is a batch operation. A single request carries any number of files, and the response reports the outcome per file — one rejected file never discards the accepted ones. That is the one documented deviation from the 422 {"errors": …} validation contract of this API generation: a rejected file is a batch item, not an invalid field.

Files arrive unattached. Nothing is bound to a record here: a client uploads, keeps the returned guids and submits them with the form that owns them (fileList for a comment). Removing a file before saving is therefore purely client-side — the file stays unattached and the platform's own cron job cleans it up.

Upload files

/api/v2/file

Stores the uploaded files for the authenticated caller. Same model, validation and image downscaling as the platform's own upload widget, so both paths produce identical files.

The response carries the stored files in results and, per rejected file, its name and validation messages in errors. The status is 200 whenever the request carried at least one file — even if every single one was rejected. A request with no file at all is a malformed request and answers 422.

Notification

Always the caller's own notifications. There is no user parameter, and no action here is reachable for a guest. (The module's /api/v1 notification endpoints, which let an admin token read another user's notifications, are unaffected.)

Cursor paging instead of page numbers. The list is ordered unseen-first, newest-first, and it reorders while a user pages through it — notifications arrive, others are read. Page numbers would silently skip or repeat entries, so a page carries a nextCursor to hand back, and null once the list is exhausted. This is the one list of this API generation that does not use the {results, total, page, pageSize, pages} envelope.

The sentence comes from the server. A notification's html is the localized, module-defined phrase ("Jane commented on Post 'Release notes'") — the one part a client cannot build. Everything around it (avatar, space badge, relative time, unread marker) is data in this payload, rendered by the client.

The caller's notifications

/api/v2/notification

One page of the caller's notifications, unseen first and newest first. Grouped notifications (several likes on the same post, say) count as one entry.

A notification whose source no longer exists — its content was deleted, its class left with an uninstalled module — is dropped from the list (and from the database) instead of failing the request, so a page may contain fewer entries than limit even when nextCursor is set.
