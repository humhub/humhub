Welcome to the HumHub notification API reference, v2.

These endpoints are part of HumHub core (1.20+). The optional REST API module contributes the token authentication methods they accept and owns the older /api/v1 surface, which is documented with that module. For the design of this stack see docs/develop/concept-api.md.

Conventions of this API generation, differing from /api/v1: camelCase field names, ISO-8601 timestamps with offset, plain HTTP status codes instead of a {code, message} envelope.

Always the caller's own notifications. There is no user parameter, and no action here is reachable for a guest. (The module's /api/v1 notification endpoints, which let an admin token read another user's notifications, are unaffected.)

Cursor paging instead of page numbers. The list is ordered unseen-first, newest-first, and it reorders while a user pages through it — notifications arrive, others are read. Page numbers would silently skip or repeat entries, so a page carries a nextCursor to hand back, and null once the list is exhausted. This is the one list of this API generation that does not use the {results, total, page, pageSize, pages} envelope.

The sentence comes from the server. A notification's html is the localized, module-defined phrase ("Jane commented on Post 'Release notes'") — the one part a client cannot build. Everything around it (avatar, space badge, relative time, unread marker) is data in this payload, rendered by the client.

Requests may authenticate with any token method the REST API module offers. HumHub's own browser session is accepted too for these endpoints, which is what the platform's Vue UI uses; state-changing session requests additionally require the CSRF token.

The caller's notifications

One page of the caller's notifications, unseen first and newest first. Grouped notifications (several likes on the same post, say) count as one entry.

A notification whose source no longer exists — its content was deleted, its class left with an uninstalled module — is dropped from the list (and from the database) instead of failing the request, so a page may contain fewer entries than limit even when nextCursor is set.

Authorizations:
BearerBasicAuthSessionCookie
query Parameters
cursor
integer

nextCursor of the previous page. Omit for the first page.

limit
integer

Entries per page (default 6, maximum 50)

categories[]
Array of strings

Notification category ids to include (comment, followed, mentioned, …, plus others-no-category for notifications belonging to no category). Categories are contributed by modules; the notification settings page lists the ones an installation offers.

Omit the parameter for no category filter at all. Passing a value that matches no category — including a single empty entry — is a filter of its own and answers an empty list, which is what "no category selected" means in the UI.

seen
string
Enum: "seen" "unseen"

Restrict to seen or unseen notifications
