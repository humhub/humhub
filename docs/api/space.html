Welcome to the HumHub space API reference, v2.

These endpoints are part of HumHub core (1.20+). The optional REST API module contributes the token authentication methods they accept and owns the older /api/v1 surface, which is documented with that module. For the design of this stack see docs/develop/concept-api.md.

Conventions of this API generation, differing from /api/v1: camelCase field names, ISO-8601 timestamps with offset, plain HTTP status codes instead of a {code, message} envelope, and {results, total, page, pageSize, pages} for paginated lists.

Requests may authenticate with any token method the REST API module offers. HumHub's own browser session is accepted too for these endpoints, which is what the platform's Vue UI uses; state-changing session requests additionally require the CSRF token.

The spaces the caller may see

The platform's space list: one page of the spaces the caller may see, searched and scoped by the parameters below. Deliberately caller-NEUTRAL — the same space reads the same for everyone, which is what lets a chooser, a picker and a directory share one representation. What the caller IS to a space (member, follower, unseen items) is /space/states.

A space the caller may not see never appears, whatever the parameters say.

What the caller is to the given spaces

Membership, following and unseen items for the spaces named — the ones a client displays, never "every space of the caller": a user can be a member of a great many while a client shows one page of them.

This is where the caller context of a space lives, which is why the list above carries none of it. newItems counts what was posted since the membership's last visit and is therefore 0 without a membership. A space the caller may not see is not answered.

The caller's membership in a space

Answers what the caller's relationship to this space is, and what they may do next (see the MembershipState schema).

Reachable for a space the caller can see, is a member of, or was invited to — an invite to an otherwise invisible space has to be answerable.

Join a space, apply for membership, or accept an invite

Affirms membership. Which of the three it is follows from the current state and the space's join policy, and is decided server-side rather than by the client:

  • an open invite (state: invited) is accepted — possible even where joining on one's own is not,
  • a space that approves memberships (needsApproval: true) receives an application with the message the caller introduces themselves with,
  • any other joinable space is joined immediately.

Answers the new state, in the same shape GET returns. 403 when the space allows no self-join, when the caller is already a member or applicant, or when they are blocked.

Leave a space, withdraw an application, or decline an invite

Removes the caller's membership, whichever of the three states it is in. Answers the new state, like the other two verbs.

Removing a membership that does not exist is a success (the answer is simply the none state). 403 for the space owner, who cannot leave their own space, and for a space whose configuration does not let its members leave.
